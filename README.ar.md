# منصة الشطرنج — Chess Hub

منصة ويب ثنائية اللغة (العربية والإنجليزية) لإدارة ملفات لاعبي الشطرنج والأخبار،
**بالإضافة إلى** منصة لعب شطرنج مباشرة متعددة اللاعبين. يتحدى اللاعبون المسجّلون
بعضهم البعض ويلعبون مباريات مصنّفة مباشرة، مع التحقق من كل نقلة على الخادم
وساعات زمنية يديرها الخادم. ويتولى المشرفون إدارة كتالوج اللاعبين والأخبار
والإشراف على المجتمع.

> **English:** [README.md](README.md) — الوثيقة الإنجليزية أكثر تفصيلًا.

---

## المزايا

- عرض وإدارة ملفات لاعبي الشطرنج والأخبار بالعربية والإنجليزية.
- تسجيل المستخدمين وتأكيد البريد الإلكتروني برمز OTP.
- لعب شطرنج مباشر مع **التحقق من النقلات على الخادم** ودفع التحديثات فورًا
  عبر WebSocket بدل الاستعلام المتكرر.
- مباريات مصنّفة وغير مصنّفة، مع أنظمة وقت وزيادة زمنية (Fischer).
- ترتيب اللاعبين وسجل المباريات وحساب تقييم Elo.
- تحديات بين اللاعبين، محادثة داخل المباراة، ورسائل مباشرة مع إمكانية الحظر.
- لوحة تحكم للمشرفين لإدارة اللاعبين والأخبار والمستخدمين والمباريات والرسائل.
- ربط حساب المستخدم بملف لاعب بعد موافقة المشرف (هوية فقط، دون صلاحية تعديل).
- رفع صور مع إعادة ترميزها والتحقق من محتواها الفعلي.
- دعم كامل لاتجاه الكتابة من اليمين إلى اليسار (RTL).

## التشغيل المحلي

```bash
git clone https://github.com/HamzaAshour949/chess.git
cd chess
npm install
cp .env.example .env
```

أنشئ مفتاح توقيع وضعه في `.env` تحت `JWT_SECRET`:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

ثم شغّل قاعدة البيانات وعبّئها بالبيانات وابدأ التطبيق:

```bash
npm run db:start && npm run db:seed && npm run dev
```

- واجهة المستخدم (مع إعادة التحميل التلقائي): <http://localhost:3000>
- الخادم وواجهة WebSocket: <http://localhost:8080>

استخدم المنفذ **3000** أثناء التطوير، فهو يمرّر `/api` و`/uploads` و`/socket.io`
إلى الخادم تلقائيًا.

للتشغيل بالطريقة نفسها المستخدمة في الإنتاج (عملية واحدة على منفذ واحد):

```bash
npm run build && npm start   # http://localhost:8080
```

### ملاحظة عن قاعدة البيانات

يشغّل الأمر `npm run db:start` السكربت [`scripts/mongo-dev.sh`](scripts/mongo-dev.sh)
الذي يبدأ `mongod` في مجلد `.mongo-data/` داخل المشروع كـ **مجموعة نسخ من عقدة
واحدة (replica set)**. هذا ليس تفصيلًا شكليًا: لا توفّر MongoDB المعاملات
متعددة المستندات إلا في هذا الوضع، وإنهاء المباراة يحتاج إلى تحديث تقييمي
اللاعبَين وسجل المباراة كوحدة واحدة.

`npm run db:stop` لإيقافها و`npm run db:status` لمعرفة حالتها.

## حسابات التجربة

يُنشئها الأمر `npm run db:seed` ويطبعها في كل مرة.

| الدور | اسم المستخدم | كلمة المرور | الرابط |
|---|---|---|---|
| مشرف | `admin` | `Admin!2026Chess` | <http://localhost:8080/admin/login> |
| لاعب | `magnus` | `ChessHub!2026` | <http://localhost:8080/login> |
| لاعب | `hikaru` | `ChessHub!2026` | <http://localhost:8080/login> |

حسابا اللاعبين مُفعَّلان مسبقًا، فلا حاجة إلى رسالة تحقق.

> **هذه البيانات موجودة داخل المستودع.** غيّرها قبل إتاحة التطبيق لأي شخص آخر.

لتجربة مباراة كاملة بنفسك: سجّل الدخول باسم `magnus` في نافذة عادية وباسم
`hikaru` في نافذة خاصة (لأن النافذتين تتشاركان `localStorage` خلاف ذلك)، ثم
أنشئ تحديًا من أحدهما واقبله من الآخر — ستظهر النقلات على الرقعتين فورًا.

## أهم القرارات في التصميم

### هويتان منفصلتان تمامًا

`admins` و`users` مجموعتان مختلفتان. المشرف ليس لاعبًا يحمل خانة إضافية، ولا
يوجد أي مسار يحوّل أحدهما إلى الآخر. ودور الحساب **مُوقَّع داخل الرمز وهو
جمهوره المقصود**، لذلك يُرفض رمز أُصدر لجهة إذا استُخدم للجهة الأخرى. كما
يُعاد قراءة الحساب مع كل طلب، فيسري الحظر أو الكتم أو الحذف فورًا.

### قائمة النقلات هي مصدر الحقيقة

تُخزَّن المباراة كقائمة نقلات بصيغة UCI. أما `fen` و`pgn` و`moveCount` فهي
**نسخ مشتقة** يُعاد بناؤها مع كل نقلة. ويترتب على ذلك أمران:

1. يمكن رصد **التكرار الثلاثي**، لأن وضعية FEN وحدها لا تحمل تاريخ المباراة.
2. لا يمكن لأي عبث بالنسخة المخزّنة أن يُثبّت وضعية غير قانونية. وهناك اختبار
   يعيد كتابة FEN إلى وضعية رابحة، فتُمحى ببساطة عند النقلة التالية.

الأمر `npm run db:repair` يعيد بناء هذه النسخ لكل المباريات عند الحاجة.

### التزامن

كل تغيير في الحالة هو **تحديث مشروط**، فلا يمكن لطلبين متزامنين أن ينجحا معًا:
النقلة تُطبَّق فقط إذا لم يتغيّر `version`، وقبول التحدي فقط ما دامت المباراة
`open`، وإنهاء المباراة فقط ما دامت `active` مع حارس إضافي يمنع احتساب النتيجة
مرتين. ولكل حالة اختبار يُطلق الطلبات في اللحظة نفسها.

### الساعات

تُحفظ الأزمنة بالميلي ثانية ويديرها الخادم. ومع كل نقلة يُخصم الوقت المستهلك
وتُضاف الزيادة الزمنية؛ واستخدام الميلي ثانية يمنع التراكم التدريجي للخطأ لصالح
اللاعب. ويُفحص انتهاء الوقت عند كل قراءة للمباراة، فتُحسم المباريات المهجورة
تلقائيًا. وإذا انتهى وقت لاعب بينما لا يملك خصمه مادة كافية لكش مات، تُحتسب
**تعادلًا** وفق قوانين الاتحاد الدولي.

### الزمن الحقيقي

تُستخدم غرف Socket.IO: غرفة لكل مباراة، وغرفة للردهة، وغرفة لكل لاعب للرسائل
المباشرة. وتبقى واجهة REST كاملة ومرجعية، مع استعلام احتياطي بطيء (كل 30 ثانية
أثناء الاتصال) حتى يعمل التطبيق خلف أي وسيط يحجب WebSocket.

### ربط ملف اللاعب (حسّاس أمنيًا)

يمكن للاعب طلب ربط حسابه بملف لاعب في الكتالوج. الربط في اتجاه واحد ويمنح
**الهوية فقط**: لا يضبطه إلا مشرف يوافق على الطلب، ولا يوجد أي مسار يتيح للاعب
ضبطه بنفسه، والربط **لا يمنح أي صلاحية تعديل** على الملف — وهناك اختبار يسجّل
الدخول بحساب مرتبط ويحاول تعديل الملف فيُرفض. كما يضمن فهرس فريد ألّا يُربط
الملف الواحد بحسابين.

## الأمان

- كلمات المرور مشفَّرة بـ bcrypt، ورموز OTP تُخزَّن مُجزّأة لا كنص صريح.
- كل المدخلات تُتحقَّق عبر Zod عند حدود الطلب.
- الصور المرفوعة يُعاد ترميزها بالكامل قبل حفظها؛ لا يُوثق بامتداد الملف
  إطلاقًا، وتُزال بيانات EXIF، والأسماء عشوائية.
- حدود لمعدل الطلبات على كل نقطة تستقبل مدخلات، وأشدّها على تسجيل الدخول.
- ترويسات أمان وسياسة CSP فعلية عبر helmet.
- قائمة CORS محدودة، ولا تُقبل القيمة `*` أبدًا.
- الروابط تُزال من محادثة المباراة للحد من الاحتيال خارج المنصة.
- الملفات السرية مثل `.env` مستثناة من Git.

### قبل النشر

- غيّر `JWT_SECRET` وكلمات مرور الحسابات التجريبية.
- اضبط `NODE_ENV=production` و`APP_URL` الصحيح.
- اضبط `CORS_ORIGINS` على نطاقك.
- لا تفعّل `TRUST_PROXY=1` إلا خلف وسيط عكسي تتحكم به.
- فعّل مصادقة MongoDB.
- اضبط `BREVO_API_KEY` لإرسال رسائل التحقق فعليًا.
- استخدم HTTPS.
