# منصة الشطرنج — Chess Hub

منصة ويب ثنائية اللغة (العربية والإنجليزية) لإدارة ملفات لاعبي الشطرنج والأخبار،
**بالإضافة إلى** منصة لعب شطرنج مباشرة متعددة اللاعبين. يتحدى اللاعبون المسجّلون
بعضهم بعضًا، أو يُقرَن بينهم تلقائيًا، ويلعبون مباريات مصنّفة مباشرة مع التحقق من
كل نقلة على الخادم وساعات زمنية يديرها الخادم. ويتولى المشرفون إدارة كتالوج
اللاعبين والأخبار والإشراف على المجتمع.

> **English:** [README.md](README.md) — الوثيقة الإنجليزية أكثر تفصيلًا، وفيها
> القائمة الكاملة لمسارات API ومتغيرات البيئة.

---

## المزايا

**اللعب**

- اقتران سريع حسب نظام الوقت، وردهة للتحديات المفتوحة مع عوامل تصفية، وتحدٍّ
  مباشر للاعب بعينه يمكنه قبوله أو رفضه، مع إشعار فوري.
- تحريك القطع بالنقر أو بالسحب، ونقاط تُظهر النقلات القانونية، واختيار قطعة
  الترقية، وأصوات للنقلات، ونقلات تظهر فورًا ثم تُلغى إن رفضها الخادم.
- ساعات يديرها الخادم مع زيادة Fischer. النقلة الأولى لكل طرف لا تُحتسب من
  الوقت، لكن يجب أن تُلعب خلال 45 ثانية وإلا أُلغيت المباراة دون تغيير التقييم.
- الاستسلام، والإلغاء قبل النقلة الثانية، وعروض التعادل (عرض التعادل بينما عرض
  الخصم قائم يُعدّ اتفاقًا)، والمطالبة بالفوز عند انتهاء وقت الخصم.
- مباراة ثأرية بألوان معكوسة، وتنزيل PGN ونسخه، وتصفّح النقلات بمفاتيح الأسهم،
  وقلب الرقعة.
- التكرار الثلاثي وقاعدة الخمسين نقلة و"الباتّ" ونقص المادة تُحتسب تلقائيًا.

**المجتمع**

- صفحة عامة لكل لاعب (`/u/:username`) فيها تاريخ التقييم والسجل وآخر المباريات
  وحالة الاتصال، مع بحث عن اللاعبين.
- محادثة داخل المباراة ورسائل مباشرة مع إشعار القراءة وشارات غير المقروء والحظر
  وإعدادات الإشعارات.
- ترتيب اللاعبين، وصفحة لمتابعة المباريات المباشرة، وآخر المباريات.
- ربط الحساب بملف لاعب في الكتالوج بعد مراجعة المشرف.

**الحساب**

- تأكيد البريد برمز لمرة واحدة، واستعادة كلمة المرور بالبريد، وتغييرها، و"تسجيل
  الخروج من كل الأجهزة"، ورفع صورة شخصية، واختيار لغة الواجهة، وحذف الحساب (تُخفى
  بياناته وتبقى مبارياته المنتهية سليمة).

**لوحة التحكم**

- إدارة اللاعبين والأخبار مع رفع الصور، والخبر المميّز، ولاعب الشهر، وبطل
  البطولة، ومحرّر لكل نصوص الواجهة باللغتين.
- الإشراف على المباريات (إلغاء، وإبطال مع عكس Elo، وإيقاف المحادثة)، والمحادثات
  والرسائل، وطلبات الربط، والمستخدمين (حظر، وكتم، وتفعيل، وفك ربط).

**في كل مكان**

- دعم كامل لاتجاه الكتابة من اليمين إلى اليسار مع عزل صحيح للأسماء والنقلات،
  وصيغ الجمع العربية كاملة، وضبط اللغة قبل أول رسم للصفحة.
- تحديثات فورية عبر Socket.IO مع استعلام احتياطي، وتنبيهات، ونوافذ تأكيد.
- احترام تفضيل تقليل الحركة، وتركيز واضح للوحة المفاتيح، وتصميم يناسب الجوال.

## التشغيل المحلي

أمر واحد يشغّل كل شيء:

```bash
git clone https://github.com/HamzaAshour949/chess.git
cd chess
bun run up
```

يقوم الأمر [`bun run up`](scripts/up.ts) بما يلي:

1. يثبّت الاعتماديات (فورًا إن لم يتغيّر شيء).
2. في أول تشغيل، يُنشئ `.env` من `.env.example` بمفتاح `JWT_SECRET` جديد.
3. يتأكد أن المنفذين 8080 و3000 غير مشغولين، ويذكر البرنامج الذي يشغلهما إن كانا مشغولين.
4. يشغّل MongoDB المحلية (إلا إذا أشار `MONGODB_URI` إلى خادم آخر).
5. يعبّئ قاعدة البيانات إن كانت فارغة، ولا يمسّ البيانات الموجودة أبدًا.
6. يشغّل الخادم والواجهة، ثم يطبع العنوان وحسابات التجربة بعد أن يستجيب كلاهما.

**يوقف Ctrl+C كل ذلك**، ومعه MongoDB (أما إن كانت تعمل من قبل فتُترك كما هي).
ويفتح الأمر `bun run up --open` المتصفح أيضًا.

وللقيام بالخطوات يدويًا:

```bash
bun install
cp .env.example .env    # ثم اضبط JWT_SECRET:
bun -e "console.log(crypto.getRandomValues(new Uint8Array(48)).toHex())"
bun run db:start && bun run db:seed && bun run dev
```

- واجهة المستخدم (مع إعادة التحميل التلقائي): <http://localhost:3000>
- الخادم وواجهة WebSocket: <http://localhost:8080>

استخدم المنفذ **3000** أثناء التطوير. يمرّر Vite المسارين `/api` و`/uploads` إلى
الخادم، أما اتصال Socket.IO فيذهب مباشرة إلى المنفذ 8080، لأن وسيط WebSocket في
Vite يعتمد على دالة من Node لا يوفّرها Bun. لهذا يتضمن `CORS_ORIGINS` في ملف
`.env` النموذجي العنوان `http://localhost:3000`.

للتشغيل بالطريقة نفسها المستخدمة في الإنتاج (عملية واحدة على منفذ واحد):

```bash
bun run build && bun run start   # http://localhost:8080
```

لا توجد خطوة بناء للخادم: يشغّل Bun الملفات في `server/src` كما هي.

### ملاحظة عن قاعدة البيانات

يشغّل الأمر `bun run db:start` السكربت [`scripts/mongo-dev.sh`](scripts/mongo-dev.sh)
الذي يبدأ `mongod` في مجلد `.mongo-data/` داخل المشروع كـ **مجموعة نسخ من عقدة
واحدة (replica set)**. هذا ليس تفصيلًا شكليًا: لا توفّر MongoDB المعاملات
متعددة المستندات إلا في هذا الوضع، وإنهاء المباراة يحتاج إلى تحديث تقييمي
اللاعبَين وسجل المباراة كوحدة واحدة.

`bun run db:stop` لإيقافها و`bun run db:status` لمعرفة حالتها.

## حسابات التجربة

يُنشئها الأمر `bun run up` عندما تكون قاعدة البيانات فارغة (أو `bun run db:seed`)، ويطبعها عند كل تشغيل.

| الدور | اسم المستخدم | كلمة المرور | الرابط |
|---|---|---|---|
| مشرف | `admin` | `Admin!2026Chess` | <http://localhost:3000/admin/login> |
| لاعب | `magnus` | `ChessHub!2026` | <http://localhost:3000/login> |
| لاعب | `hikaru` | `ChessHub!2026` | <http://localhost:3000/login> |

حسابا اللاعبين مُفعَّلان مسبقًا، فلا حاجة إلى رسالة تحقق.

> **هذه البيانات موجودة داخل المستودع.** غيّرها قبل إتاحة التطبيق لأي شخص آخر.

لتجربة مباراة بنفسك: سجّل الدخول باسم `magnus` في نافذة عادية وباسم `hikaru` في
نافذة خاصة (لأن النافذتين تتشاركان `localStorage` خلاف ذلك)، ثم اضغط **اقتران
سريع** بنظام الوقت نفسه في النافذتين، فتُفتح المباراة على الرقعتين.

## أهم القرارات في التصميم

### هويتان منفصلتان تمامًا

`admins` و`users` مجموعتان مختلفتان. المشرف ليس لاعبًا يحمل خانة إضافية، ولا
يوجد أي مسار يحوّل أحدهما إلى الآخر. ودور الحساب **مُوقَّع داخل الرمز وهو
جمهوره المقصود**، لذلك يُرفض رمز أُصدر لجهة إذا استُخدم للجهة الأخرى. كما
يُعاد قراءة الحساب مع كل طلب، فيسري الحظر أو الكتم أو الحذف فورًا.

ويحمل رمز اللاعب رقم إصدار (`tokenVersion`) يزداد عند تغيير كلمة المرور أو
استعادتها أو "تسجيل الخروج من كل الأجهزة" أو حذف الحساب، فتبطل كل الرموز السابقة.

### قائمة النقلات هي مصدر الحقيقة

تُخزَّن المباراة كقائمة نقلات بصيغة UCI. أما `fen` و`pgn` و`moveCount` فهي
**نسخ مشتقة** يُعاد بناؤها مع كل نقلة. ويترتب على ذلك أمران:

1. يمكن رصد **التكرار الثلاثي**، لأن وضعية FEN وحدها لا تحمل تاريخ المباراة.
2. لا يمكن لأي عبث بالنسخة المخزّنة أن يُثبّت وضعية غير قانونية. وهناك اختبار
   يعيد كتابة FEN إلى وضعية رابحة، فتُمحى ببساطة عند النقلة التالية.

الأمر `bun run db:repair` يعيد بناء هذه النسخ لكل المباريات عند الحاجة.

### التزامن

كل تغيير في الحالة هو **تحديث مشروط**، فلا يمكن لطلبين متزامنين أن ينجحا معًا:
النقلة تُطبَّق فقط إذا لم يتغيّر `version`، وقبول التحدي فقط ما دامت المباراة
`open`، وإنهاء المباراة فقط ما دامت `active` مع حارس إضافي يمنع احتساب النتيجة
مرتين، وإبطالها مرة واحدة فقط. وتضمن فهارس فريدة جزئية ألّا يكون للاعب أكثر من
تحدٍّ مفتوح في الردهة، ولا أكثر من تحدٍّ مباشر مفتوح لكل خصم. ولكل حالة اختبار
يُطلق الطلبات في اللحظة نفسها.

### الساعات

تُحفظ الأزمنة بالميلي ثانية ويديرها الخادم. ومع كل نقلة يُخصم الوقت المستهلك
وتُضاف الزيادة الزمنية؛ واستخدام الميلي ثانية يمنع التراكم التدريجي للخطأ لصالح
اللاعب.

- **النقلة الأولى لكل طرف مجانية**، وتبدأ الساعة مع ردّ الأسود كما في المنصات
  الكبرى. ولكل طرف `FIRST_MOVE_TIMEOUT_SECONDS` (45 ثانية) للعب نقلته الأولى،
  وإلا أُلغيت المباراة دون تصنيف.
- تحفظ كل مباراة جارية موعد انتهاء حالتها الحالية (`deadlineAt`). وتمرّ **مهمة
  دورية** كل 3 ثوانٍ فتحسم المباريات المتأخرة وتُبلغ اللاعبَين، حتى لو لم يكن
  أحد يفتح الرقعة، وتسحب التحديات التي لم يقبلها أحد خلال
  `CHALLENGE_TTL_MINUTES` (30 دقيقة).
- ويُجرى الفحص نفسه أيضًا عند كل قراءة للمباراة وكل محاولة نقلة.
- إذا انتهى وقت لاعب بينما لا يملك خصمه مادة كافية لكش مات، تُحتسب **تعادلًا**
  وفق قوانين الاتحاد الدولي.

### الزمن الحقيقي

تُستخدم غرف Socket.IO: غرفة لكل مباراة، وغرفة للردهة، وغرفة لكل لاعب للرسائل
المباشرة والتحديات وإشعارات الحساب. ويعرف الخادم من المتصل من اللاعبين، ومن هنا
تأتي علامة "متصل". وتبقى واجهة REST كاملة ومرجعية، مع استعلام احتياطي (كل 30
ثانية أثناء الاتصال، وكل ثانيتين عند انقطاعه) حتى يعمل التطبيق خلف أي وسيط يحجب
WebSocket. ولا يقبل العميل أي تحديث إلا إذا كان رقم `version` فيه أحدث مما يعرضه.

### ربط ملف اللاعب (حسّاس أمنيًا)

يمكن للاعب طلب ربط حسابه بملف لاعب في الكتالوج. الربط في اتجاه واحد ويمنح
**الهوية فقط**: لا يضبطه إلا مشرف يوافق على الطلب، ولا يوجد أي مسار يتيح للاعب
ضبطه بنفسه، والربط **لا يمنح أي صلاحية تعديل** على الملف — وهناك اختبار يسجّل
الدخول بحساب مرتبط ويحاول تعديل الملف فيُرفض. كما يضمن فهرس فريد ألّا يُربط
الملف الواحد بحسابين، وتُرفض الطلبات الأخرى المعلّقة على الملف نفسه تلقائيًا عند
الموافقة على أحدها.

## الاختبارات

```bash
bun run test
```

218 اختبارًا في 12 ملفًا، تستغرق نحو 35 ثانية، وتعمل على قاعدة بيانات اختبار
منفصلة (`chess_hub_test`) لا تمسّ بيانات التطوير، إذ ترفض أدوات الاختبار أي قاعدة
لا ينتهي اسمها بـ `_test`.

يُتحقَّق من توليد النقلات باختبار **perft** مقابل ست وضعيات مرجعية معروفة؛ فأي
نقلة ناقصة أو زائدة في أي مكان من الشجرة تُغيّر النتيجة. وبهذا تُثبَت قواعد
القانونية التي يقوم عليها أمان المنصة كلها، بدل الاكتفاء بالثقة في المكتبة.

كما تغطي الاختبارات الحالات التي يسهل الخطأ فيها ويصعب ملاحظته: النقلات
المتزامنة، وقبول التحدي أو الاقتران السريع من لاعبين في اللحظة نفسها، وانتهاء
الوقت ومهلة النقلة الأولى، والمهمة الدورية، والتكرار الثلاثي، وعكس التقييم عند
إبطال مباراة، وإبطال الرموز، والحدود بين صلاحيات المشرف واللاعب والزائر.

## الأمان

- كلمات المرور مشفَّرة بـ bcrypt، وتُرقّى التجزئات الأضعف عند تسجيل الدخول
  التالي. ورموز التحقق تُخزَّن مُجزّأة لا كنص صريح، وتُحجز كل محاولة تحقق قبل
  فحص الرمز، فلا تتجاوز المحاولات المتوازية الحد المسموح.
- كل المدخلات تُتحقَّق عبر Zod عند حدود الطلب.
- الصور المرفوعة يُعاد ترميزها بالكامل قبل حفظها؛ لا يُوثق بامتداد الملف
  إطلاقًا، وتُزال بيانات EXIF، والأسماء عشوائية.
- حدود لمعدل الطلبات على كل نقطة تستقبل مدخلات، وأشدّها على تسجيل الدخول،
  وتُحتسب لكل حساب لا لكل عنوان IP بعد تسجيل الدخول.
- ترويسات أمان وسياسة CSP فعلية عبر helmet، ولا تصل رسائل الأخطاء الداخلية إلى
  المستخدم.
- قائمة CORS محدودة، ولا تُقبل القيمة `*` أبدًا.
- أسماء المستخدمين فريدة دون اعتبار لحالة الأحرف، وأسماء مثل `admin` و`support`
  محجوزة لمنع انتحال الشخصيات.
- الروابط تُزال من محادثة المباراة للحد من الاحتيال خارج المنصة، والحظر يمنع
  الرسائل والتحديات في الاتجاهين.
- يرفض الخادم العمل في الإنتاج بمفتاح `JWT_SECRET` النموذجي أو دون وسيلة لإرسال
  البريد.
- الملفات السرية مثل `.env` مستثناة من Git.

### قبل النشر

- غيّر `JWT_SECRET` وكلمات مرور الحسابات التجريبية (أو لا تُعبّئ بيانات التجربة).
- اضبط `NODE_ENV=production`، واجعل `APP_URL` عنوان موقعك العام بـ `https://`.
- اترك `CORS_ORIGINS` فارغًا ما دام الخادم نفسه يقدّم الواجهة.
- لا تفعّل `TRUST_PROXY=1` إلا خلف وسيط عكسي تتحكم به.
- فعّل مصادقة MongoDB.
- اضبط `BREVO_API_KEY` لإرسال رسائل التحقق واستعادة كلمة المرور فعليًا.
- استخدم HTTPS.

## النشر

### باستخدام Docker

```bash
cp .env.example .env              # اضبط JWT_SECRET وPRODUCTION_APP_URL وBREVO_API_KEY
docker compose up -d --build      # التطبيق على المنفذ 8080 مع MongoDB كمجموعة نسخ
docker compose exec app bun server/src/db/seed.ts   # بيانات تجريبية (اختياري)
```

يقرأ Compose المتغيرين `PRODUCTION_APP_URL` و`PRODUCTION_CORS_ORIGINS` بدل
`APP_URL` و`CORS_ORIGINS`، حتى لا تصل قيم التطوير في `.env` إلى الحاوية.

تُبنى الصورة على ثلاث مراحل: بناء الواجهة، ثم تثبيت اعتماديات الخادم اللازمة
للإنتاج وحدها، ثم نسخها مع `server/src` إلى صورة Bun صغيرة تعمل بمستخدم غير
مميّز، مع فحص صحة على `/api/health`. وتُحفظ الصور المرفوعة في وحدة تخزين مستقلة.

### دون Docker

```bash
bun install --frozen-lockfile
bun run build
bun run start          # تُنشأ الفهارس تلقائيًا عند التشغيل
```

عملية واحدة تقدّم الواجهة وAPI وWebSocket على المنفذ نفسه. وخلف وسيط عكسي، مرّر
ترقية WebSocket للمسار `/socket.io` واضبط `TRUST_PROXY=1`. ويُرجع
`GET /api/health` الرمز 503 عند انقطاع قاعدة البيانات.

### ملاحظات عن Bun

- مكتبة `bson` مثبّتة على الإصدار 7.2.0 عبر `overrides`، لأن الإصدار 7.3 يستدعي
  دالة من V8 لا يوفّرها Bun، فيفشل تحميل Mongoose.
- `sharp` مُدرجة في `trustedDependencies` ليتمكن سكربت التثبيت من تنزيل ملفها
  التنفيذي.
